# 项目定位

## 1. 起点:半导体行业的文档治理观察

实习期间在半导体行业(景嘉微)观察到三个不同于互联网公司的文档治理特征:

1. **文档是法定资产**:流片报告、IP 授权、工艺规范需保存 7-10 年应对监管审计
2. **实体溯源高频**:"X 规范谁批的"、"过去 3 年变更几次"、"谁是决策人"
   ——这类查询在合规驱动行业是日常,在互联网公司一年问一次
3. **全文搜索失效**:大量 PDF/扫描件/表格,关键信息以实体关系形式存在

这三点构成 Graph RAG 的甜区:entity-centric、长期沉淀、跨文档关联。

## 2. 项目演化

实习期间提出过对应的内部工具提案,因 ROI 优先级考量未立项
(PM 的判断:对芯片公司,把同样资源投到流片质量上 ROI 高 10 倍)。
但"半导体行业文档治理是真痛点"这一判断本身没被否决。

离职后,用公开标准 benchmark 独立完成这个项目的架构验证版本:
schema-constrained 的 closed schema 抽取 + 项目文档 corpus + 置信度过滤,
用 200 篇公开项目文档和 420 条合成控制问题支撑可复现评估。

## 3. 适用边界(诚实说明)

这套架构最适合三类场景:
- 强合规行业(金融/医疗/半导体/航空航天)
- 大型组织 onboarding
- B2B 知识资产化产品

对快速迭代、文档存活周期短的互联网产品场景,ROI 有限。
这个边界判断来自实习经历。

## 4. 技术选型

- Graph RAG > vector-only RAG:文档是 entity-centric,跨文档实体共现密集
- Closed schema > open schema:实体类型可控,审计 traceable
- 自研增量集中在 LightRAG / RAGAnything 的薄弱接缝处,不重写上游

## 5. Corpus

PURE SRS (学术需求 benchmark) + GitHub 公开 PRD + 公开技术博客
——三源真实数据,当前本地 corpus 共 200 篇、约 35 万词,可复现可公开评审。
